# SABR transport provenance

Adapt SmartTube's `exoplayer-amzn-2.10.6/library/sabr` from local revision `bf9cd3142`, preserving source behavior and notices. The transport is adapted to the existing Media3 1.11.0 engine under `nl.neerdael.milkbeat.sabr`; no second ExoPlayer engine or SmartTube application singleton is introduced. Provider endpoints/authentication remain in the private `youtube-video` plugin. Protobuf definitions are generated with the maintained protobuf toolchain, not handwritten codecs.

The maintainer explicitly requests these SmartTube playback pieces, including SABR. Media3's resolved artifacts have no equivalent SABR module. Protocol, format selection, token/CDN recovery and reload/seek behavior require fixture and native verification before claiming support.

## Verified adaptations

- Generate upstream protobuf schemas in `:media3-sabr-protocol` with protoc and Java-lite 4.35.1. The protobuf Gradle plugin 0.9.5 runs in a JVM library because it does not support the current Android library DSL.
- Use Media3's `ExtractorInput`; its methods no longer declare `InterruptedException`.
- Media3 1.11.0 has no `Format.lastModified` and its `Metadata.Entry` no longer extends `Parcelable`. Preserve the unsigned last-modified bits, xTags and audio-track identity in immutable format metadata.
- Replace SharedUtils equality and first-match helpers with Java equivalents, and use Android's URI implementation for query handling.
- Remove verbose upstream parser logging that prints signed URLs, opaque reload tokens or SABR context messages. Retain protection-status and reload events for the playback layer.
- Reject truncated UMP integers and headers that exceed the signed integer range before constructing a part. Preserve the upstream UMP encoding, which differs from protobuf varints.

The transport now includes adapted source/period/chunk classes and Media3 container adapters. The Matroska adapter uses the maintained ForwardingExtractor because Media3 makes read final; it propagates failures instead of swallowing them. The upstream unused experimental frame splitters are omitted: the active transport uses Media3's MP4/Matroska extractors. Protection-status, reload and empty-response events reach bound renewal through typed exceptions without inventing an HTTP status. Native sustained playback and paired-provider verification remain required before claiming SABR support.

## Transport correctness verification

Use Media3 `DefaultExtractorInput` over a demultiplexing `DataReader` for the complete read/skip/peek contract. Container positions count media bytes rather than UMP control bytes. Reject early EOF inside declared UMP and media payloads; only clean EOF before an optional complete read returns false.

Track selection updates the stream's full unsigned `(itag, lastModified, xTags)` identity and current audio-track ID before each request. Matching requires every supplied discriminator; an itag-only fallback applies only to an explicitly incomplete selected identity. Reconcile cached formats when selections change and preserve discarded in-flight segments through a switch back. Identity-based ownership prevents a released old source from clearing a replacement source's selection.

Persist normalized millisecond timing and the nested authoritative itag in completed headers. Use completed header ends to schedule subsequent requests and detect repeated responses with no progress. Send the current load position explicitly when adapting to a newly selected tuple, so an uninitialized rendition cannot restart at zero. Convert interrupted or corrupt response bodies to typed `NO_PROGRESS` renewal with redacted diagnostic causes. Disable Media3's physical-byte retry after any response bytes: a raw SABR POST cannot range-resume a partly consumed envelope. Preserve genuine HTTP statuses and whole-request/CDN retry before response bytes. Media3 chunk boundaries are finite estimates constructed before the response headers arrive; actual header timing controls progression and end-of-stream, so a short final segment is requested. Activate live metadata and server-seek control parts; refresh live timelines on metadata events without polling and clamp live seeks to the advertised DVR range. Unknown durations retain Media3's unset sentinel and use a nonnegative default position. Native audio expiry reports the accepted `serverAbr.url` even when `AudioStream.url` is a marker or placeholder. The host owns validated relative expiration through its monotonic playback descriptor lifetime; the transport does not override that lifetime using an unverified TV wall clock and a URL epoch parameter.

For the selected live format, reject a noninitialization header whose sequence does not follow the last completed segment before registering it or exposing media bytes. Nearby mismatches abandon the rejected response and retain the tolerance adjustment in the next whole POST at the same media cursor. Limit this resynchronization to three attempts; persistent or distant mismatches reach typed `NO_PROGRESS` renewal. Reset the adjustment after completed selected media or a seek/reset, without letting discarded other-track or initialization segments reset the retry budget. This is a host correctness fix: the pinned upstream only logs sequence differences and does not construct its mismatch exception.

`SabrTransportRegressionTest` records seven initial RED regressions against the pre-fix implementation. `SabrContainerExtractorTest` uses real FFmpeg-produced MP4 (`sidx`, fragmented atoms and `moov/meta`) and WebM media through maintained Media3 extractors with arbitrary UMP and network fragmentation. `SabrChunkLoadingTest` exercises actual `ContainerMediaChunk.load()` calls, a 500 ms final fragment, sequential request timing, seek and live metadata. `ServerAbrPresentationTest` also uses Media3's actual adaptive selection for video request transitions and checks dubbed-audio identity/release ownership. These local fixtures establish transport/container behavior; live account authorization and sustained native 2160p decoding remain separate acceptance evidence.

## Initialization and request policy

Preserve SmartTube's non-null initialization-range marker even when the backend supplies no byte range. The generic presentation now enters Media3's `InitializationChunk` first, with an initialization POST that excludes the chosen format from `selected_format_ids`. Subsequent `ContainerMediaChunk` POSTs retain the same processor's initialized-format cache. The marker does not issue an HTTP range request. A synthetic AAC fixture exercises a server that omits initialization metadata once a format is advertised as selected; this reproduces the verified native handshake failure without publishing captured signed or account-bound data.

Stamp `NextRequestPolicy.backoff_time_ms` on receipt using Media3's monotonic `Clock`. Defer each processor's next request until that deadline and post one callback through Media3's `HandlerWrapper` to the period's existing loading callback. Repeated chunk evaluations do not move the deadline; a new policy replaces the timer. Seeking/resetting consumed ranges preserves an outstanding server delay, and releasing the source cancels the callback. Policies remain scoped to the stream/processor that received them, matching the separate audio/video streamer contexts. No sleeping network thread, polling loop or wake lock is introduced.

Initialization responses can contain complete media segments in addition to format/container initialization. Media3's maintained `InitializationChunk` forwards those samples into its output queues. Preserve the completed media cursor and buffered range when creating the first following container chunk; restarting an empty media-chunk queue at zero repeats those samples and stalls the nondecreasing playback clock. A second synthetic AAC source-loop regression models an initialization response containing both initialization and the full first segment, verifies the first 90 samples remain available, and checks that the next POST retains its consumed range and requests the following segment. The resulting 180 sample timestamps are strictly increasing, with no first-segment replay or PCM discard.

A control-only response with a complete positive `NextRequestPolicy` from that same response is an acknowledgment of deferred loading. Signal it internally to Media3's cancelable-load path, remove the empty acknowledgment chunk and wait through the existing backoff callback before opening a fresh whole POST. This does not advance the media cursor, add a buffered range or invoke provider renewal. Initialization acknowledgments keep requesting initialization until the maintained extractor has its formats. Response-scoped state prevents a cached older policy from masking an empty or truncated response; any media header also excludes the control-only acknowledgment path. Empty/zero-backoff/truncated policy responses and incomplete media retain typed `NO_PROGRESS` handling.

`SabrDeferredResponseTest` drives actual `ChunkSampleStream`, `Loader`, initialization/container chunks and sample queues with a deterministic in-memory executor. It verifies that acknowledged empty chunks are removed, loading/buffered positions remain zero during backoff, no POST occurs before the deadline, fresh POSTs start at byte zero, initialization remains selected-format-free until ready, and all subsequent container samples are delivered. Malformed-response regressions cover stale policy state and dangling/zero-length media headers.

Derive the enabled-track bitfield from the requested media track, independently of optional video dimensions. Missing height suppresses only the optional sticky/manual resolution fields; a video request remains video-only, and an audio request remains audio-only even when another selected video format has a known height.

Treat a live presentation's optional supplied duration as a non-authoritative snapshot. Keep its global manifest duration unset so Media3 exposes a dynamic window; live metadata updates the available window without turning it into finite VOD. Prepared-source regressions cover finite and absent live durations before/after live-head updates, alongside a finite static VOD timeline.

Carry an accepted video playback's existing outer DVR flag through its bound source into the transport factory's runtime live-seekability setting. Live timelines expose seeking only for explicitly accepted DVR playback, and live-head updates preserve that capability. VOD remains seekable; direct live music presentations with no outer DVR evidence conservatively default to unseekable. This is source configuration only: the plugin wire model, SDK and immutable provider artifacts are unchanged. Prepared timeline regressions cover explicit DVR true/false through metadata updates, and the host regression resolves/binds the provider response and prepares the runtime-held source while preserving its accepted media item.

Milkbeat configures both bound video and music SABR sources with `PlayerConfig.LIVE_EDGE_GAP_MS` (10 seconds), overriding the generic transport default and manifest suggestions. A live-window regression publishes actual timelines from server metadata through both app source paths, with and without picture, and verifies the same gap used by the existing HLS/DASH live-edge policy.
